# Realtime Gateway (Hermes)

**Status:** current

## Kind
component

## Summary
The Hermes realtime entry point: the single transport the client uses to reach the authoritative validator. In production the Godot client connects to the Snapser Hermes WSS gateway (player token in the query string), which proxies a *snap-api-proxy* envelope to the BYOSnap gRPC port; locally the validator serves the *identical* envelope at `ws://localhost:5555/hermes/ws?token=<player-id>`, giving the client exactly one codepath against either backend.

## Purpose
To collapse two physically different deployments — the Snapser-hosted gateway and a developer's local validator — into *one* client codepath. By serving a byte-identical Hermes envelope locally, the client never branches on environment: it sends the same frames, unwraps the same replies, and exercises the same `ValidatorService` methods (`InitMatch`, `ValidateAction`, `CompleteMatch`) whether it is talking to the gateway or a dev box. This is the realtime conduit for the optimistic-reconcile loop, where the client plays predictively and the validator returns the authoritative state and hash.

## Design notes
The Hermes envelope codec is currently stubbed behind TODO(skeleton) markers. decodeEnvelope and encodeEnvelope accept a plain-JSON dev frame of the InnerRequest/InnerReply shape so the endpoint is exercisable before the protobufjs codec for the Hermes envelope is wired via proto.ts (loadHermesRoot). When that lands, the JSON fallback is replaced with real protobuf encode/decode and external behavior stays unchanged.

Connection lifecycle uses the Bun WebSocket handler shape: tryHermesUpgrade matches the /hermes/ws path, resolves the player id, attaches WsData, and performs server.upgrade (Bun sends the 101 itself); makeHermesWebSocketHandlers provides open/message/close. The handlers are built as a factory so tests can inject a ValidatorService.

The naming mirrors the Snapser Hermes pattern: a single ClientMessage/ServerMessage duplex multiplexing many request types via a oneof, where the snap-api-proxy message wraps a target method name plus payload bytes that the gateway proxies to a backend snap RPC (here, ValidatorService). Proto bindings are generated by tools/gen-protos.sh and must not be hand-edited.

## Data model
The wire protocol is a single duplex of `ClientMessage` / `ServerMessage` over one WebSocket, each carrying a `type` discriminator and a `oneof body`. For validator RPCs the type is `snap-api-proxy`: a `SnapApiProxyRequest` carries `request_id` (correlation), `method` (the logical RPC name), and `payload` (the serialized request bytes); the matching `SnapApiProxyResponse` echoes `request_id` and returns a gRPC-style `status_code` plus `payload` bytes. Critically, game *state* and *actions* are NEVER modelled as proto fields — they travel as canonical-JSON STRINGS inside those payload bytes, so the envelope is an opaque carrier and the determinism hash stays byte-for-byte identical on client and validator. Locally, per-socket `WsData` holds the resolved `playerId` and a short `connId`; the decoded `InnerRequest` (`method` / `requestId` / `args`) is routed and the `InnerReply` (`requestId` / `ok` / `data` / `error`) is wrapped back.

## Invariants & constraints
- The local WS endpoint and the production gateway serve the IDENTICAL envelope, so the client has exactly ONE codepath; `hermes-ws.ts` and the gRPC transport both route to the SAME ValidatorService methods with identical semantics.
- Game state and player actions are NEVER modelled as proto messages — they ride as canonical-JSON strings inside the opaque `payload` bytes. Re-modelling them as proto fields would silently break the byte-for-byte determinism-hash parity contract between the GDScript and TypeScript engines.
- Player identity is resolved per-environment by `config.isLocal`: locally the `?token=` query param is the self-stamped player id; in production the gateway stamps a verified `User-Id` header. An upgrade with no usable id is rejected (401).
- The transport is behaviorally a pass-through: it unwraps, routes, and re-wraps, but performs no rule logic. All authoritative enforcement lives behind ValidatorService; the gateway/local paths must stay behaviorally one path.
